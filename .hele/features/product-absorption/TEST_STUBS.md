# Test Stubs — product-absorption

Derived from the approved v1.0 product description and its changelog slice map before inspecting tests. No execution plan was read. Stable IDs describe behavior; technical proof belongs in Coverage.

<stub id="TS-001" increment="001" rule="BR-1" kind="integration" status="pending">
**Title:** Initialize only missing prerequisites
**Given** an existing product has no Hele memory.
**When** absorption begins.
**Then** the one-time design participation question and settings/catalog initialization precede product reading; an existing answer is reused and task tracking is required.
</stub>

<stub id="TS-002" increment="001" rule="BR-1" kind="integration" status="pending">
**Title:** Do not equate a binary check with usable task storage
**Given** the prerequisite binary check succeeds.
**When** absorption assesses task tracking readiness.
**Then** binary availability alone is not claimed to prove project database usability; successful database operations provide that evidence.
</stub>

<stub id="TS-003" increment="001" rule="BR-2" kind="integration" status="pending">
**Title:** Survey the whole product through background specialists
**Given** absorption has usable prerequisites.
**When** the initial read phase runs.
**Then** named background readers cover domain behavior, user experience, history and schema, plus design only when enabled; they respect concurrency and the conductor remains available after dispatch.
</stub>

<stub id="TS-004" increment="001" rule="BR-2" kind="integration" status="pending">
**Title:** Keep evidence-led survey findings durable and read-only
**Given** specialists investigate candidate capabilities.
**When** they report their findings.
**Then** task records contain paths, symbols or test names and conflicts; product documents, tests, visible behavior and constraints outrank names/comments, with no extra notes files or product edits.
</stub>

<stub id="TS-005" increment="001" rule="BR-3" kind="integration" status="pending">
**Title:** Partition recognizable capabilities with exclusive ownership
**Given** the whole-product survey is available.
**When** features and historical slices are proposed.
**Then** features describe user capabilities, each product file has one owner, overlapping feature readers do not run together and slices use oldest-first three-digit numbering with English names.
</stub>

<stub id="TS-006" increment="001" rule="BR-3" kind="integration" status="pending">
**Title:** Group history into meaningful slices without invented motives
**Given** a capability spans multiple commits or more than eight candidate slices.
**When** the snapshot is consolidated.
**Then** independently shippable slices can group commits; over eight slices merges the smallest supporting slices with explanation, current rules follow evidence, ordering follows history and motives are recorded only when evidenced.
</stub>

<stub id="TS-007" increment="001" rule="BR-4" kind="integration" status="pending">
**Title:** Preserve existing descriptions unless refresh is requested
**Given** a proposed capability already has a matching description.
**When** its slug and aliases are searched before writing.
**Then** the snapshot identifies it as already documented, ordinary approval does not rewrite it and wording differences do not create a duplicate; refresh requires the human request.
</stub>

<stub id="TS-008" increment="001" rule="BR-5" kind="integration" status="pending">
**Title:** Present a saved complete snapshot before feature writes
**Given** read work is complete.
**When** the proposed cut is presented.
**Then** every increment has a row and evidence links, material doubts carry recommendations, applicable existing capabilities are listed, consolidation is saved, read tasks close and scratch is removed; feature documents and shared maps await approval apart from initialization.
</stub>

<stub id="TS-009" increment="001" rule="BR-6" kind="integration" status="pending">
**Title:** Treat snapshot acceptance as acceptance of its recommendations
**Given** the full snapshot and recommendations are presented.
**When** the human selects option 1.
**Then** the complete cut and stated recommendations are approved before feature writing starts.
</stub>

<stub id="TS-010" increment="001" rule="BR-6" kind="integration" status="pending">
**Title:** Revise only challenged areas and re-present the full snapshot
**Given** the human selects correction or gives corrective free text.
**When** the snapshot is revised.
**Then** no feature artifacts are written; only affected capabilities, partitions or challenged evidence and dependents are reread, prior valid survey work is reused and the entire revised snapshot is presented for approval.
</stub>

<stub id="TS-011" increment="001" rule="BR-7" kind="integration" status="pending">
**Title:** Write approved current-state memory once
**Given** a new capability is in the approved snapshot.
**When** its feature memory is written.
**Then** approved v1.0 current rules, flows and scope, independent scenarios, historical records and per-slice validation are produced; testable rules and a slice/rule changelog are registered once with names, summaries, aliases and document versions but no feature status.
</stub>

<stub id="TS-012" increment="001" rule="BR-7" kind="integration" status="pending">
**Title:** Refresh existing memory without duplicating it
**Given** the human authorized refreshing a documented capability.
**When** the refresh is written.
**Then** its living product description and version are patched rather than registering another capability; unsupported motives remain explicitly unrecorded.
</stub>

<stub id="TS-013" increment="001" rule="BR-8" kind="integration" status="pending">
**Title:** Keep historical completion separate from executable delivery
**Given** an absorbed historical slice is recorded.
**When** its historical plan is produced or refreshed.
**Then** it is built and marked as absorption with an empty task list, never ready or assigned a build queue; existing absorbed plans stay frozen and later slices append at the next number without implying green QA.
</stub>

<stub id="TS-014" increment="001" rule="BR-8" kind="integration" status="pending">
**Title:** Disclose the absorbed-plan format contradiction
**Given** the supplied historical template contains section tags despite prohibiting them.
**When** the approved snapshot records that format.
**Then** the existing template body is preserved and the inconsistency remains explicit rather than silently claiming a corrected format.
</stub>

<stub id="TS-015" increment="001" rule="BR-9" kind="integration" status="pending">
**Title:** Create shared maps only for applicable missing surfaces
**Given** absorption considers shared data and design maps.
**When** the approved write phase runs.
**Then** only an existing application schema with a missing map or enabled design with a missing map creates one; existing maps remain intact and no design specification or database-change proposal is created.
</stub>

<stub id="TS-016" increment="001" rule="BR-9" kind="integration" status="pending">
**Title:** Avoid inventing application surfaces for this harness
**Given** the absorbed product is hele-skills with design disabled and no application database.
**When** shared maps are considered.
**Then** task storage is not treated as the application schema, neither shared map is created and shipped design capabilities remain inventoried.
</stub>

<stub id="TS-017" increment="001" rule="BR-10" kind="integration" status="pending">
**Title:** Resume open work and recover an unwritten snapshot
**Given** absorption context is lost with open tasks or a completed saved snapshot not yet written.
**When** the conversation resumes.
**Then** ready work continues without a duplicate survey, or the saved full snapshot returns to approval/correction; every task in an epic closes before leaving it.
</stub>

<stub id="TS-018" increment="001" rule="BR-10" kind="integration" status="pending">
**Title:** Distinguish completed absorption from new delivery
**Given** write work and its files already exist.
**When** the process resumes or a new product idea arrives after closure.
**Then** completed writing leads to the final report; after closure a new idea enters ordinary Hele delivery instead of another survey.
</stub>

<stub id="TS-019" increment="001" rule="BR-11" kind="integration" status="pending">
**Title:** Patch wrong rules without reopening frozen history
**Given** feedback identifies a wrong rule after absorption.
**When** the correction is authorized.
**Then** only the living rule, version/changelog, affected scenarios and increment evidence refresh; frozen plans remain untouched and the whole app is not resurveyed.
</stub>

<stub id="TS-020" increment="001" rule="BR-11" kind="integration" status="pending">
**Title:** Route feature-cut corrections and new ideas appropriately
**Given** later feedback changes the feature cut or proposes new behavior.
**When** the request is handled.
**Then** a wrong cut returns to affected reading and a complete revised snapshot before writes; new product work follows ordinary delivery.
</stub>

<stub id="TS-021" increment="002" rule="BR-12" kind="integration" status="pending">
**Title:** Derive independent acceptance behavior before proof mapping
**Given** an approved product description and slice map are available.
**When** acceptance scenarios are authored.
**Then** product expectations are derived without reading implementation plans, each has a stable identity, originating three-digit increment and rule reference, and only afterward are existing tests mapped separately; new scenarios remain pending until current proof supports them.
</stub>

<stub id="TS-022" increment="002" rule="BR-13" kind="integration" status="pending">
**Title:** Assess each slice while reusing valid current proof
**Given** approved slices share existing evidence.
**When** QA selects and records verification.
**Then** each slice is assessed under the shared policy, valid shared runs are reused rather than repeated per folder and selection follows behavior and actual evidence even without production changes.
</stub>

<stub id="TS-023" increment="002" rule="BR-13" kind="integration" status="pending">
**Title:** Distinguish missing, blocked and failing proof honestly
**Given** required proof is missing, execution is prevented or an assertion fails.
**When** the current QA assessment is recorded.
**Then** missing proof is pending with an owner, prevented validation is blocked and failed assertions are failing; source inspection and historical results alone never become passing evidence.
</stub>

<stub id="TS-024" increment="002" rule="BR-14" kind="integration" status="pending">
**Title:** Prepare validation artifacts without triggering remediation
**Given** an absorbed increment reaches QA assessment.
**When** reports are written.
**Then** each slice receives a QA report and prepared verification artifact without ordinary QA routing, implementation/fix tasks against frozen plans or starting the human walk.
</stub>

<stub id="TS-025" increment="002" rule="BR-14" kind="integration" status="pending">
**Title:** Use optional honest current-state visuals
**Given** visual evidence is considered during absorption.
**When** screenshots or E2E selection is reported.
**Then** useful current-state screenshots follow quality and retention rules, no fictional before/after is produced and justified zero new E2E or screenshots leaves unresolved proof explicit.
</stub>

<stub id="TS-026" increment="002" rule="BR-15" kind="integration" status="pending">
**Title:** Close writing and report gaps separately from completion
**Given** all feature and increment artifacts have been written.
**When** absorption closes its write phase.
**Then** the index and every increment QA task close before the write epic, and the final report counts features, historical increments, scenarios, evidence and gaps or blockers with file links; built history never hides incomplete validation.
</stub>

<stub id="TS-027" increment="002" rule="BR-15" kind="integration" status="pending">
**Title:** Respect language and disclose the adapted runtime
**Given** absorption reports completion using this Codex adaptation.
**When** artifacts and chat are presented.
**Then** files follow artifact language and reports follow chat language; strict-model versus inheritance remains a limitation and Claude Code remains the shipped distribution, without claiming native Codex support.
</stub>
